# 決定記録

段階間の契約。実装より先に決めた。変更するときは理由を追記して残す（消さない）。
**まだ実装していない決定には「未実装」と書く。** 実装が済んだらその行を消す。

---

## D-001 PROV エンティティの粒度 — 画像 1 枚 = 1 Entity

**決定**: 画像 1 枚を 1 つの `prov:Entity` とする。セッションはグラフの単位であって
Entity ではない。派生は `wasDerivedFrom`（reified `prov:Derivation`）で繋ぐ。

**Entity の同一性は画像の内容ハッシュ（SHA-256）で決める。**
IRI は `{base}/resource/image/{sha256}`。

**なぜ**
- 内容が変われば IRI が変わるので、§不変条件「元の絵を加工しない」が構造として守られる。
  既存 Entity を書き換える操作が原理的に書けない
- 同じ画像を 2 回作れば同じ IRI に収束する。重複が自然に畳まれる
- セッション単位にすると「どの版が論文に載ったか」が引けない。これはスコープの中心なので落とせない

**捨てたもの**: セッション = 1 Entity。枝分かれを表現できない。

## D-002 Activity に記録するもの — 再実行できる情報を全部

**決定**: 1 回の生成 = 1 つの `prov:Activity`。IRI は `{base}/resource/activity/{id}`。
次を必須項目とし、**1 つでも欠けたら記録を拒否する**（`assertReproducible`）。

| 項目 | 述語 | 例 |
|---|---|---|
| プロンプト全文 | `provision:prompt` | "a minimal line drawing of ..." |
| モデル識別子 | `provision:model` | "z-image-turbo-4bit" |
| seed | `provision:seed` | 42 |
| 開始・終了時刻 | `prov:startedAtTime` / `prov:endedAtTime` | ISO 8601 |

任意項目: `provision:negativePrompt` / `steps` / `guidance` / `width` / `height` / `provider`。

**なぜ**: 「再実行できる」が価値の柱。欠けても書けてしまう設計だと、欠けたまま溜まって
後から復元できない。書き込み時に落とすのが唯一効く場所。

**捨てたもの**: 「あとで補完する」方式。補完されないまま残ることが geo-logo で実証済み。

## D-003 意図（自然言語の指示）の置き場所 — Activity の属性

**決定**: 利用者が出した指示（「もっと余白を」「配色を寒色に」）は
`provision:intent` として **Activity に置く**。辺は素の `wasDerivedFrom` のまま保つ。

**なぜ**
- PROV の標準から外れない。`prov:Derivation` に独自属性を足すと、
  素の PROV しか読まない側（asterism / prov-jsonld-viz）で意図が落ちる
- 「どの指示でこうなったか」は Activity を辿れば出る。辺に置く必然性がない
- 1 つの Activity が複数の入力を使う場合、辺ごとに意図を分けても意味を持たない

**捨てたもの**: 辺の属性（`provision:intentOn` など）。連携が切れる代償に見合わない。

## D-004 名前空間 — 素の PROV ＋ `provision` の最小拡張

**決定**: `@vocab` は `http://www.w3.org/ns/prov#`。画像生成に固有の語だけを
`provision:` に置く。`matprov` は取り込まない（名前空間の切り方だけ真似る）。

```json
{
  "@context": [
    {"@vocab": "http://www.w3.org/ns/prov#"},
    "https://openprovenance.org/prov-jsonld/context.jsonld",
    "https://kumagallium.github.io/provision-schema/context.jsonld"
  ],
  "@graph": []
}
```

**なぜ**: 独自語彙を減らすことがそのまま相互運用性になる。連携できることが差別化の本体。

## D-005 直列化の形 — reified な PROV-JSONLD（openprovenance 形式）

**決定**: 関係は実体ノードとして書く。`Usage` / `Generation` / `Association` / `Derivation`
を `@graph` に並べ、値は `[{"@value": ...}]` の配列形式にする。

**なぜ**: `prov-jsonld-viz`（`~/develop/prov-jsonld-viz/index.html`）が
`item["@type"] === "Usage" | "Generation" | "Association"` を見て辺を描く実装だから。
受け入れ条件「書き出した JSON-LD が prov-jsonld-viz で開ける」はこの形でしか満たせない。

**関係ノードに `@id` は付けない。** viz は `@id` を持つ項目を無条件にノードとして描くため、
付けると Usage / Generation / Association が孤立した点として画面に散らばる（実機で確認）。
`@id` を落とせば辺だけが描かれる。JSON-LD としては空白ノードになるだけで問題ない。

**参照した外部リソースにもノードを置く。** 置かないと viz が「端点の無い辺」を作ろうとして
cytoscape が例外を投げ、**辺が 1 本も描かれない**（実機で確認。ノード 12・辺 0 になった）。
置くのは IRI と `prov:Entity` だけで、中身は主張しない——それは asterism 側の言うことである。

**`prov:Derivation` の実体ノードは書かない。** viz は辺を描かず、孤立ノードが増えるだけだった。
派生は Entity 側の `prov:wasDerivedFrom` として直接持たせてあり、SPARQL からはそちらで引ける
（`?new prov:wasDerivedFrom ?old`）。詳細が要る場合も `wasGeneratedBy` + `used` で辿れる。

## D-006 データへの接合点 — 「人間が参照した」として `prov:used` だけ張る

**決定**: 図版が元データ（asterism の curve / sample）と繋がる辺は、
生成 Activity の `prov:used` として書く。**`prov:wasDerivedFrom` は張らない。**
責任者は `prov:wasAssociatedWith` の人間 Agent。

**なぜ**
- 画像生成モデルはプロンプトを消費しただけで、測定曲線を読んでいない。
  「この曲線から派生した」と書けば**それは来歴の嘘**になる
- 一方「著者がこの曲線を見て、この図を作らせた」は実在する事実で、
  `prov:used` ＋ 人間 Agent への `wasAssociatedWith` で正確に書ける
- 新語彙が 1 つも要らない。asterism 側は素の PROV でこれを読める

**捨てたもの**: 図版とデータを `wasDerivedFrom` で直結すること。
横断クエリは書きやすくなるが、グラフが嘘をつく。

**副作用**: `wasDerivedFrom` は画像の親だけを指すので、
`prov:wasDerivedFrom*` の推移閉包が「画像の系譜」だけを正しく辿る。
外部リソースが混ざらないのは、この分離のおかげ。

## D-007 RDF への出口 — N-Triples を自前で書く

**決定**: asterism（Oxigraph）へ載せるための N-Triples は、JSON-LD ライブラリで
展開せず、`src/prov/ntriples.ts` が素の PROV の IRI を直接書く。

**なぜ**: JSON-LD の展開は `@context` をネットワークから取りに行く。
`provision-schema` の URL はまだ実在せず、openprovenance も外部依存になる。
グラフの形はこちらが完全に決めているので、直接書く方が決定論的でオフラインで動く。
`@context` を配信し始めたら、後から標準の展開に差し替えてもよい（出力は一致するはず）。

## D-008 後から分かったことは、書き換えずに「表明」として足す

**決定**: 生成のあとで分かること——「この版はこのデータに基づく」「この版が Figure 2 として
載った」——は、**既存の Entity / Activity を書き換えずに、別の `prov:Activity` として記録する**。

```
表明 Activity
  prov:used            <対象の画像>
  prov:used            <外部データ IRI>        ← 参照のとき
  prov:generated       <fabio:Figure>          ← 掲載のとき
  prov:wasAssociatedWith <人間 Agent>
  prov:startedAtTime   <言った時刻>
```

**なぜ**
- 不変条件（元の絵を加工しない・記録を書き換えない）をそのまま守れる
- **「生成時に分かっていたこと」と「後から人が主張したこと」が混ざらない。**
  いつ・誰が言ったかまで残るので、主張の責任が追える
- 掲載は世界の側で起きた事実であって、絵が変わったわけではない。
  Entity に後から属性を足すと、その区別が消える

**生成の Activity と表明の Activity の見分け方**: `provision:prompt` を持つかどうか。
表明は絵を作らないので prompt が無い。読み戻しはこれで判別する（新しい語彙を足さずに済む）。

**掲載の語彙は FaBiO を使う**（`fabio:Figure`、`http://purl.org/spar/fabio/`）。自作しない。
図版の IRI は**載った先の識別子から作る**（`{doi}#figure-2`）ので、
同じ論文の同じ図なら誰が記録しても同じ IRI に収束する。

**捨てたもの**: Entity に `publishedAs` のような属性を後から足すこと。書けてしまうが、
「いつ誰が言ったか」が消え、生成時の事実と区別できなくなる。

## D-009 `@context` は自分で配信する

**決定**: `provision` の `@context` を **GitHub Pages（`docs/schema/context.jsonld`）で実際に配信する**。
IRI も `https://kumagallium.github.io/PROVision/schema/context.jsonld#` に揃えた。

**なぜ**: 実在しない URL を書いておくと、JSON-LD を素直に展開する側（他のツール、
将来の自分）が 404 を踏む。D-007 で自前 N-Triples にして回避してはいるが、
**それは出口の都合であって、書き出したファイルが嘘をついてよい理由にはならない。**

## D-010 内容ハッシュは**画素**に取る。ファイル全体ではない

**決定**: Entity の IRI を決める内容ハッシュは、PNG の **IHDR ＋ 展開した IDAT**
（＝寸法と画素そのもの）から取る。ファイル全体のバイト列は数えない。

**なぜ**（2026-08-20 の実測）: 同じ prompt / model / seed で 2 回出したところ、
**画素は 3,146,752 バイトすべて一致**し、違っていたのは mflux が書き込む
`iTXt`（XMP）と `eXIf` だけだった——どちらにも生成時刻が入る。

ファイル全体を数えていると、**同じ絵でも毎回別の IRI になる**。
D-001 の「同じ内容は同じ Entity に収束する」が実質破れていた。
「再実行できる」という主張も、検査すれば必ず失敗する状態だった。

`recordGeneration` にバイト列をそのまま渡すと今も全体を数える。
呼び側は `imageContentDigest()` を通すこと（型では強制できないので、注記で残す）。

**この修正より前に記録した版は、旧方式のハッシュのまま**。書き換えない——
来歴は書き換えないという原則が、自分たちの都合より優先する。

## D-011 出し直して食い違ったら `prov:alternateOf` で繋ぐ

**決定**: 同じ指定で再実行して別の絵が出たとき、新しい版は元の版の
`prov:alternateOf` とする。`wasDerivedFrom` は張らない。

**なぜ**: 前の絵を材料にしたわけではないので、派生と書けば嘘になる（D-006 と同じ筋）。
PROV には「同じものを指す別の実体」を表す語があるので、それを使う。
新しい語彙は要らない。

**副作用**: 会話の切り出し（根ごとの連結成分）で、食い違った版が
別の会話として独立してしまうのを防げる。`roots()` と `rootOf()` は
`alternateOf` を辿って元の会話へ寄せる。

## D-012 画像ツールの定義を 1 か所に畳む

**決定**: ツールの性質（説明・引数の許可・前提条件・実行先・例）は `src/ai/tools.ts` の
`IMAGE_TOOLS` だけに書く。LLM へ渡す一覧・引数の検証・実行先の振り分け・回帰テストは、
すべてそこから導く。**ツールの性質をここ以外へ書かない。**

**なぜ**
- 定義が散っていたとき、1 つ足すのに 3 ファイル 11 箇所を触る必要があった。
  そのうち 1 箇所（`prompt` の許可）を落とし、正しく選ばれた計画が検証で捨てられて
  無関係な文字が描かれた。注意深さではなく構造の問題
- LLM へ渡す説明文が実装と別に書かれていると、片方だけ古くなる。
  説明を定義から組み立てれば、その食い違いが起きない
- `examples` をそのまま回帰テストへ流せる。誤分類が見つかったら 1 行足すだけで、
  以後は構造が守る（利用者が画面で見つけて報告する必要がない）

**形は MCP のツール定義に合わせる**（name / description / inputSchema）。
将来ツール群を MCP サーバとして出すなら、この配列を写せばよい。

**捨てたもの**: 各層でツールを列挙する書き方。読む場所は近いが、足し忘れが必ず起きる。

## D-013 受け取れない引数は、弾かずに落とす

**決定**: 宣言していない引数がツール計画に混ざっていても、計画ごと拒まず、
その引数だけを無視して実行する。**危険な値**（範囲外の数値、制御文字、長すぎる文字列）は
従来どおり拒む。

**なぜ**: 計画を拒むと規則ベースへ落ちて **別のツールが動く**。利用者から見ると
「頼んでいない絵が出た」になる。無視すれば、選ばれたツールはそのまま正しく動く。
実測: `image.wordmark` に書き直し文が付いてきたのを弾いた結果、生成側へ落ちて
`asterism` のはずが `DHX` と描かれた。

**捨てたもの**: 「宣言にないものは全部エラー」。厳密だが、壊れ方が利用者に見えない。

## D-014 確定的に作った構造は、来歴から作り直す

**決定**: 確定的なツールが作った構造（ワードマークの帯と文字）へ手を入れる指示は、
**その版の画素を編集せず、元になった画像まで戻して同じツールを引数違いで実行する**。
判断材料として、計画時に `parentTool`（親を作ったツール）と `parentText`
（親のワードマークが描いた文字列）をプランナーへ渡す。

**なぜ**
- 確定的に置いた帯と文字は、画素になった時点で「帯」「文字」という構造を失う。
  拡散モデルはそれを知らないので、「間の余白を調整して」と頼むと全体を描き直し、
  **文字ごと消す**（実測。プロンプトも振り分けも正しかったのに結果が壊れた）
- 一方 Jimp の `trim` が扱えるのは外周の余白だけで、要素の間には届かない。
  両方の隙間に落ちる指示があり、そこに落ちると壊れた絵が黙って返る
- 来歴には「この版はワードマークで、文字は asterism」と残っている。
  **構造を覚えているのは来歴だけ**なので、そこから作り直せば文字は消えない
- 同じ仕組みで、既に帯がある版へ重ねて二重になる問題も起きなくなる

**捨てたもの**: 画素から構造を推し量る方法（帯の位置を検出するなど）。
背景や字色が変われば崩れるうえ、来歴に答えが書いてあるのに読まないのは筋が悪い。

**戻る先は「最初の元絵」で、画面上の親ではない**。作り直しを繰り返すとき、画面上の親には
既に帯が乗っているので、そこへ戻ると重なる。親自身が作り直しだったなら、そのとき使った
元絵（`conditioningImage`）を引き継ぐ。判断は `ProvGraph.rebuildBaseOf` に置き、
呼ぶ側では持たない——同じ判断を 2 か所に書いて、片方だけ直し損ねた（実測）。

**この決定が効く範囲**: 確定的なツールが作った版だけ。拡散モデルだけで作られた絵に
同じ指示が来ても構造は復元できないので、そこは従来どおり生成編集へ回る。

## D-015 別 PC でのビット一致は目標にしない。**食い違いの原因が特定できること**を目標にする

**決定**: 「同じ指定なら別の PC でも同じ画素が出る」を PROVision の保証に含めない。
代わりに次の 2 つを保証する。

1. **食い違ったと分かること** — 内容ハッシュ（D-010）と `prov:alternateOf`（D-011）で既に済んでいる
2. **なぜ食い違ったか特定できること** — 実行環境（モデル重みの指紋、ツールの版、機種、
   チップ、**GPU コア数**、macOS の版と**ビルド番号**）を `prov:SoftwareAgent` に
   実測値で載せる ← **これが D-015 で足すもの**

   機種識別子だけでは足りない。`MacBookPro18,2` は M1 Max の 24 コア GPU と 32 コア GPU の
   両方を指す（BTO の差を吸収する）。ここで取りこぼすと、下の表で「✗」と書いた当の要因が
   来歴から消える。OS も同様で、同じ 26.5.1 でもビルドが違えば Metal の実装が変わりうる。

**この記録で言えることと、言えないこと**（非対称なので注意）

| 問い | 答えられるか |
|---|---|
| 記録した項目のどれが違うか | ○ 文字列の突き合わせで完全に決まる |
| 環境は同一だったか | **✗** 記録していない変数が残る。「違う」は言えるが「同じ」は言えない |
| その差が絵を変えた原因か | **✗** 相関どまり。因果は言えない |

つまりこの機能が返すのは**原因の証明ではなく、容疑者の絞り込み**である。
そう書いておかないと、次はこの機能自身が過大な主張になる。

**なぜ**: 拡散モデル＋Metal では、別 PC でのビット一致を原理的に閉じられない。

| 変動要因 | 固定できるか |
|---|---|
| MLX / mflux のバージョン、モデルの量子化重み | ○ ピン留め・digest で同定できる |
| Apple Silicon の世代差、同一チップ名での GPU コア数差 | ✗ 浮動小数点の集約順序が変わる |
| Metal カーネルの実装差 | ✗ |
| コンテナで環境ごと固定する | ✗ Docker on macOS は GPU を渡せない |

閉じられないものを保証だと書けば、**D-010 で直したのと同じ失敗**——「再実行できるという
主張が、検査すれば必ず失敗する状態」——が再発する。来歴の道具が守るべき順序は、
できることを増やすより先に、書いてある主張が全部真であることの方である。

**そもそもこの道具の問いはビット一致を要求していない**。答えたいのは「どの版が載ったか、
それはどのデータのどの版に基づくか」で、図版は既に存在している。作り直す必要がない。
別 PC で違う絵が出ること自体は失敗ではない。失敗は「違うのに同じだと思われること」と
「なぜ違うのか分からないこと」の 2 つだけで、前者は解決済みだった。

**捨てたもの**: 実行環境を丸ごと固定して再現を保証する路線（コンテナ、シード固定の
リファレンス実装）。Metal を使う以上そこへは行けないうえ、行けたとしても
上の問いには何も足さない。

## D-016 再現の等級はツールごとに違う。**等級を書き出したファイルに載せる**

**決定**: ツールを「別 PC でどこまで再現するか」で 3 等級に分け、Activity へ
`provision:reproducibility` として記録する。等級は executor から導き、
[`src/ai/tools.ts`](../src/ai/tools.ts) の 1 か所だけに書く（D-012 と同じ理由）。

| 等級 | executor | 意味 |
|---|---|---|
| `deterministic` | `jimp` | 同じ入力なら、どの PC でも同じ画素。演算が整数・確定的 |
| `environment-dependent` | `inpaint` / `background` | モデルとバージョンが一致すれば同じ。乱数は使わない |
| `stochastic` | `image-model` | 環境が変われば変わりうる。D-015 の対象 |

**なぜ**: 系譜は等級の違う辺が混ざったものになる。「Jimp で正方形に切り、mflux で
描き直し、LaMa で消した」なら、再現する辺としない辺が 1 本の鎖に同居する。
**全体を「再現する／しない」で語ると、必ずどちらかが嘘になる。**

**なぜグラフに書くのか（コードから引かせないのか）**: 書き出した JSON-LD は
PROVision の外——prov-jsonld-viz や asterism の SPARQL——で読まれる。
ツール名から等級を引くのに PROVision のコードが要る形にすると、
**書き出したファイル 1 つで完結する**という前提（README 冒頭）が崩れる。

**等級は executor 単位で持ち、ツール単位では持たない**。ツールを 1 つ足したとき、
等級の書き忘れで無印の辺が生まれるのを防ぐ——D-012 がツール定義を畳んだのと同じ動機。

## D-017 差分は出す。**原因だとは書かない**

**決定**: `prov:alternateOf` で繋がった 2 版を突き合わせ、記録した項目のうち
違ったものだけを画面と SPARQL に出す（[`src/prov/compare.ts`](../src/prov/compare.ts)、
[`queries/reproducibility-drift.rq`](../queries/reproducibility-drift.rq)）。
ただし文言は**「容疑者」で止める**。「原因」とは書かない。

**なぜ**: D-015 で足した環境の記録は、突き合わせて初めて役に立つ。
人が JSON-LD を目で比べる状態では、「なぜ食い違ったか特定できる」という
D-015 の保証が、実質的に果たされていない。

**なぜ原因と書かないか**（この決定の本体）

| 問い | 答えられるか |
|---|---|
| 記録した項目のどれが違うか | ○ 文字列の突き合わせで完全に決まる |
| 環境は同一だったか | ✗ 記録していない変数が残る |
| その差が絵を変えた原因か | ✗ 相関どまり |

**「違う」は言えるが「同じ」は言えない**という非対称がある。全項目が一致しても、
Metal のカーネル実装や実行時のメモリ圧は記録していないので、環境が同一だった
証明にはならない。ここを画面の文言で曖昧にすると、**食い違いを暴くための機能が
それ自体、検査に耐えない主張になる**——D-010 と D-015 で 2 度踏んだ形である。

そのため差分が 0 件のときも「一致した」で止め、「同じ環境だった」とは書かない。
出した項目数（`compared`）も一緒に返す。「何件見たうえで 0 件か」が分からないと、
0 件が「一致」なのか「そもそも見ていない」なのか区別できない。

**足りない記録もこの決定で埋めた**

| 足したもの | なぜ要るか |
|---|---|
| `provision:role` | Agent の IRI は環境ごとに変わる（D-015）。**環境をまたいで「同じツール」だと言えるのはこれだけ** |
| `provision:commandTemplate` | `PROVISION_IMAGE_COMMAND` を差し替えた差が、他の属性からは見えない |
| Python の版 | 依存の解決が変わりうる |
| GPU コア数 | 機種識別子は BTO の差を吸収する。`MacBookPro18,2` は M1 Max の 24 コアと 32 コアの両方を指す |
| macOS のビルド番号 | 同じ 26.5.1 でもビルドが違えば Metal の実装が変わりうる |

**コマンドは生の argv ではなく雛形で残し、ホームは `~` に畳む**。
一時ファイル名は毎回変わるので、そのまま入れると毎回「違う」と出て差分の意味が消える。
利用者名を書き出したファイルへ載せないためでもあり、**利用者名が違うだけの 2 台を
同じコマンドとして突き合わせられる**ようにするためでもある。

**捨てたもの**: 画像そのものの差分（画素比較）。どこが違って見えるかは目で分かるし、
答えたいのは「なぜ違うか」の方である。

## D-018 1 つの指示から複数の候補を出す。**兄弟であって `alternateOf` ではない**

**決定**: 1 回の送信で最大 4 枚まで出せるようにする。N 枚は**同じ親から生えた兄弟の
Activity** として記録する。`prov:alternateOf` は使わない。**新しい語彙は足さない。**

| 揃うもの | 版ごとに違うもの |
|---|---|
| `used`（親）、`provision:intent`（利用者の生の言葉） | `seed`、`provision:prompt`（実行された全文） |

**なぜ `alternateOf` ではないか**: あれは「**同じ指定なのに食い違った**」ための語である
（D-011）。seed が違えば指定そのものが違うので、食い違いではない。ここを混ぜると、
再実行で食い違いを検出する仕組み（D-011・D-017）が候補出しのノイズで埋まる。

**なぜ「1 回の操作で出した 3 枚」だとは記録しないのか**（この決定の本体）

3 枚が同じ親を指し、同じ `intent` を持つことは、**既に記録として完全に書かれている**。
足りないのは「1 回の送信だったか、3 回に分けたか」だけで、これは**道具の操作の記録で
あって、図版の来歴ではない**。PROVision が残すと決めたのは後者である。

| 問い | 既存の記録で言えるか |
|---|---|
| 並列に探索したのか、逐次に直したのか | ○ 同じ親を指す兄弟か、鎖か |
| どれを選んだのか | ○ 子ができた枝が選ばれた枝。子のない兄弟は選ばれなかった |
| 1 回の操作だったのか | ✗ ——だが、絵の来歴ではない |

**捨てたもの**: `prov:Plan` ＋ `prov:qualifiedAssociation` で「同じ指示から出た候補群」を
束ねる形。素の PROV で表せるので D-004 には反しないが、束ねて得られるのは操作の回数
だけで、既存の記録に足すものが無い。読む側が Association の reify を追う手間だけが増える。

> **2026-08-26 撤回（D-022）。** この判断は**親がある候補しか見ていなかった**。
> 親が無ければ兄弟になりようがなく、根が N 個生まれる。束ねて得られるのは操作の回数
> ではなく、**その候補群がどこから始まったか**だった。D-022 で Plan を置く。

「どれを選んだか」を明示したくなったら、生成時ではなく **D-008 の表明**として後から足す。
選択は生成の瞬間には決まっていない（3 枚出してから選ぶ）ので、生成の記録に混ぜると嘘になる。

**候補の作り分けは 2 段階**

| 段 | 何を変えるか | 前提 |
|---|---|---|
| A | `seed` だけ。prompt は同一 | 無し。規則ベースでも動く |
| B | `prompt` を候補ごとに書き分ける | 「指示の AI 解釈」が有効なこと |

A で出るのは**同じ狙いのサンプル違い**であって、方向性は変わらない。
「方向性の違う候補を 3 つ」は B でしか満たせない。

**B は、いまのプランナーの縛りと正面から衝突する。** 書き直しの指示には
`Do not invent styles, moods, or elements the user did not request` と書いてある
（[`src/ai/planner.ts`](../src/ai/planner.ts)）。方向の違う案を作らせるのは、
**頼まれていないものを足させること**そのものである。

そのため B は、**利用者が方向の違いを明示的に頼んだときだけ**有効にする。縛りは緩める
のではなく、**外した事実を記録に残す**——実行された全文は `provision:prompt`、利用者の
生の言葉は `provision:intent` として既に別々に残るので、何を頼んで何が足されたかは
版ごとに突き合わせられる。ここでも新しい語彙は要らない。

**seed の決め方**: 候補ごとに独立に引き、それぞれの Activity に記録する。まとめて N 枚を
作り直す機能は作らない——1 枚ずつの再実行（`/api/rerun`）が既にあり、各 Activity は
自分の seed を持っているので、失うものが無い。

**上限は 4 枚、既定は 1 枚**。1 枚 2〜3 分の直列実行なので、4 枚で 10 分前後になる。
**N 枚のうち一部が落ちたら、落ちた分だけ記録しない**。全部やり直させると、成功した
2〜3 分を捨てることになる。

**枚数は指示から読み取らない。** 画面で選ばせる。自然言語から数を推測すると、外したときに
黙って違う枚数が出る。ただし**複数を求めている指示なのに 1 枚設定だったことには気づかせる**
——黙って 1 枚だけ出すのが、この決定を書くきっかけになった不具合そのものだった。

### 親が無い候補は、それぞれ別の会話になる（実装して分かったこと）

候補は兄弟として記録されるが、**親が無ければ兄弟になりようがない**。まだ 1 枚も無い状態で
候補を 3 つ出すと、3 つの根——つまり 3 つの会話——が生まれる。

束ねる語彙を足さないと決めた以上（上記の「捨てたもの」）、これが正しい結果である。
3 枚は材料を共有しておらず、系譜としても別物だからである。**そのうえで画面ではそう伝える。**
伏せると、利用者は 1 つの会話に 3 枚並ぶことを期待する。

> **2026-08-26 解消（D-022）。** 利用者から「1 つ頼んだのに会話が勝手に増える」と
> 指摘を受けた。**画像を共有していなくても、指示は共有している。** 指示を節点として
> 置けば連結成分は 1 つになり、伝える必要も無くなる。

## D-019 外から持ち込んだ画像は `image.import` として記録する。**来歴が始まる点を隠さない**

**決定**: アップロードした画像も Entity にするが、**Activity を伴わせる**。
`image.import` という Activity を 1 つ立て、`used` は空、`generated` はその画像とする。

**なぜ Entity だけ置かないのか**

- 会話の根は「**親を持たない生成が生んだ画像**」で定義されている
  （[`ProvGraph.roots`](../src/prov/graph.ts)）。Activity の無い Entity は根にならず、
  画面に出てこない。`rootOf` も Activity を辿る
- **いつ・誰が持ち込んだかは実在する事実で、記録できる。** Entity だけ置くと、
  その事実の置き場所が無い

**記録するもの / しないもの**

| 記録する | なぜ |
|---|---|
| 画素の内容ハッシュ | Entity の同一性そのもの（D-001・D-010） |
| **元ファイルのバイト列のハッシュ**（`provision:sourceFileDigest`） | 手元のファイルと突き合わせるため。下記 |
| 元ファイルの mediaType と**ファイル名だけ**（パスは畳む） | どのファイルだったか。利用者名を書き出さない（D-017 と同じ理由） |
| 取り込み時刻・取り込んだ人 | `startedAtTime` と `wasAssociatedWith` |

| 記録しない | なぜ |
|---|---|
| その画像がどう作られたか | **外にある。取れないものは書かない**（D-015） |

**元ファイルのハッシュを Activity に別途持つ理由**（この決定で一番効くところ）

取り込みで PNG に正規化すると、**元のファイルとバイト列が一致しなくなる**。Entity の
同一性は画素の内容ハッシュで決まる（D-010）ので、これは曲げない。だが実験画像では
「手元のこの生ファイルが、この図版の出発点だ」と言えないと、持ち込む意味の大半が失われる。

そこで **Entity の同一性は画素のまま（D-010）、取り込みという行為の記録に元ファイルの
バイト列のハッシュを足す**。載せる先が Activity なのは、それが行為の記録だからである。
Entity 側へ足すと、同じ絵を別形式で 2 回取り込んだときに Entity の同一性が割れる。

**再現の等級に `external` を足す**（D-016 の表に 1 行増える）

| 等級 | 意味 |
|---|---|
| `external` | **再現の対象外。元のファイルが要る** |

`stochastic` に潰さない。「環境が変われば変わりうる」と「そもそも記録から作れない」は
別のことで、混ぜると系譜全体の等級（`weakestReproducibility`）の意味が壊れる。
`external` は一番弱い。**これを含む系譜は、元のファイルが手元にないと再現できない。**

**executor に `import` を足す**。既存の 4 つ（image-model / jimp / inpaint / background）
のどれでもない。等級は executor 単位（D-016）なので、ここを足さずに済ませる道は無い。

**捨てたもの**: 元のバイト列をそのまま保存し、そのハッシュを Entity の同一性にする形。
D-010 を形式ごとに例外化することになり、「同じ絵は同じ Entity」（D-001）が崩れる。

## D-020 「再現するか」と「画素を作ったか」は別の軸である



**決定**: `provision:pixelOrigin` を足す。**再現の等級（D-016）とは独立した軸**として
Activity へ載せる。

| 値 | 意味 | ツール |
|---|---|---|
| `geometric` | 位置と補間だけ。内容の追加も除去もない | `image.trim` / `image.crop-square` / `image.rotate` / `image.resize` |
| `photometric` | 画素値を変えるが、**画像全体に同じ規則で**。局所的に差をつけない | `image.brightness` / `image.contrast` / `image.gamma` |
| `annotated` | 元の画素を残したまま、確定的な描画を重ねる・余白を足す | `image.wordmark` / `image.scalebar` / `image.arrow` |
| `removed` | 画素を消す（透明にする）だけ。足さない | `background.remove` |
| `synthesized` | **入力に無かった内容を作った** | `image.generate` / `image.edit` / `image.erase` / `image.compose` |
| `external` | **この画素が何を経てきたかは、この記録の外にある** | `image.import`（D-019） |

**なぜ等級と分けるのか**（この決定の本体）

| ツール | 再現の等級 | 画素の由来 |
|---|---|---|
| Jimp | `deterministic` | `geometric` |
| **LaMa / IOPaint** | `environment-dependent` | **`synthesized`** |
| rembg | `environment-dependent` | `removed` |
| mflux / FLUX.2 | `stochastic` | `synthesized` |

**LaMa が示すとおり、決定的に近いことと画素を作らないことは別である。** LaMa は乱数を
使わないが、消した領域を周囲から**描いている**。実験画像でそれをやれば、再現できようが
できまいが改ざんである。軸が 1 本しかないと、この 2 つが 1 本に潰れ、
**`environment-dependent` が「安全」と読まれる**。

**なぜ画面の注意書きではなく、書き出したファイルに載せるのか**: D-016 と同じ。書き出した
JSON-LD は PROVision の外——prov-jsonld-viz や asterism の SPARQL——で読まれる。
ツール名から引くのに PROVision のコードが要る形にすると、**ファイル 1 つで完結する**
という前提（README 冒頭）が崩れる。

**pixelOrigin は executor 単位ではなく、ツール単位で持つ**（D-016 と違う）

等級を executor 単位にしたのは「同じ実行先なら再現の性質が同じ」だからである。
画素の由来はそうではない——Jimp の回転（`geometric`）と、これから足す明るさ調整
（`photometric`）は同じ実行先だが、画素への触り方が違う。executor 単位に押し込むと、
実行先と軸が混ざった偽の executor（`jimp-geometric` など）が生まれる。

D-016 が心配した「ツールを足したときの書き忘れ」は、**`ImageToolDefinition` の必須
フィールドにすること**で防ぐ。省略可にしない。型で強制すれば、ツールを 1 つ足した時点で
コンパイルが通らない。

### 生成を使わない編集専用モード

**決定**: 設定で「生成を使わない」を選べるようにする。有効なとき、`pixelOrigin` が
`synthesized` のツールを **`validateImagePlan` の段階で拒む**。実行してから止めるのでは
遅い——LLM がそのツールを選ぶ余地が残り、選ばれた理由だけが画面に出て絵が出ない、という
分かりにくい壊れ方をする。

**落とし先を作らない**。規則ベースの既定は、編集元が無ければ `image.generate`、判断が
つかなければ `image.edit` へ落ちる（[`ruleBasedPlan`](../src/ai/planner.ts)）。
このモードではどちらも禁じられるので、**落とすのではなく「このモードでは実行できない
指示です」と理由を返す**。黙って別のツールが動くのが一番悪い（D-013 の実測）。

**モードが有効だったことは記録しない。** 記録するのは実行されたものだけである。系譜の
全 Activity の `pixelOrigin` を見れば、`synthesized` が 1 本も無いことは確定的に言える。
「そのとき設定がこうだった」は、実際に何が実行されたかより弱い主張で、足しても言える
ことが増えない（D-017 と同じ筋）。

**系譜全体は一番強い辺へ上がる**。等級が一番弱い辺へ落ちる（D-016）のと対になる。
`synthesized` が 1 本でもあれば、その版は生成を通っている。

### 画面に何と書くか——ここで止める

| 書く | 書かない |
|---|---|
| 「この系譜の N 本のうち、画素を作ったものは 0 本」 | 「この画像は改ざんされていない」 |
| 「取り込んだ画像より前は、この記録では見えない」 | （黙って伏せる） |

D-017 と同じ非対称がある。**PROVision が言えるのは「記録したツールのうち画素を作るものを
通ったか」までで、PROVision の外で加工されてから持ち込まれた画像については何も言えない。**
`external`（D-019）を系譜の集約で必ず併記するのは、この限界を画面から消さないためである。

**切り抜きが妥当かどうかは、この軸では答えない。** 都合の悪い領域を切り落とすのは
`geometric` だが、学術的には問題になりうる。PROVision の仕事は「切り抜いた」と記録する
ことであって、切り抜きの妥当性を判定することではない（D-017 と同じ線引き）。

**足りない道具**: `photometric`（明るさ・コントラスト・ガンマ）と、`annotated` の
スケールバー・矢印。いずれも Jimp で確定的に書ける。実験画像の正当な加工にはこれらが
要るので、編集専用モードを名乗るなら揃える。

> **2026-08-26 追記。** 道具を入れて分かったこと——**尺度も、どこを指すかも、PROVision には
> 分からない**。スケールバーの棒の長さ（px）も文字列も、矢印の位置も、利用者が言ったものを
> そのまま使うしかない。いずれも `toolArguments` として来歴に残るので、**その主張の責任は
> 人間 Agent にある**（D-006 と同じ筋）。こちらで推定したら、検査に耐えない主張を絵に焼く
> ことになる。
>
> 矢印の位置は**画像の大きさに対する％**で受け取る。画素で受け取ると、後からリサイズした
> ときに指す所がずれる。％なら記録としても読める。

## D-021 融合を認める。**会話は連結成分ではなく「分岐元」でたどる**

**決定**: 2 枚以上の画像を材料に 1 枚作る `image.compose` を足す。`used` に複数の親を
入れる。あわせて、**会話の定義を「根ごとの連結成分」から「`provision:branchedFrom` を
たどった主系列」へ変える。**

**PROV 側はほぼ無改造で済む**

| 既にできること | 場所 |
|---|---|
| `used` は配列 | `GenerationActivity.used` |
| `lineage()` は全親を再帰的に辿る | [`ProvGraph.lineage`](../src/prov/graph.ts) |
| `children()` は `used.includes` で引く | [`ProvGraph.children`](../src/prov/graph.ts) |

**壊れるのは会話の切り出しだけ**。`rootOf()` は `used[0]` しか見ないので、**2 つの会話に
またがって融合すると、融合した版は片方の会話にしか属さない**。もう片方から見ると、
自分の画像を材料にした版が画面に出てこない。

### なぜ「連結成分」を捨てるのか

素直に連結成分のままにすると、**別の会話から画像を 1 枚借りただけで、無関係な長い会話が
まるごと合流する**。README が「会話は別の語彙で持たない」と書いたのは、グラフと食い違う
ストアを持たないためであって、連結成分という**特定の切り出し方**に縛られるためではない。
切り出し方はグラフから導ける限り自由に選べる。

**主親は「利用者がどの版に居たか」で決まる。** 画面で版 A を選んでいて画像 B を足したなら、
主親は A である。これは既存の操作（`current` から送ると枝が生える）とそのまま一致するので、
利用者に新しい概念を持ち込まない。

### なぜ `used` の順序では表せないのか

`recordGeneration` は Activity の ID を決めるために `used` をソートしている
（[`ProvGraph.recordGeneration`](../src/prov/graph.ts)）。ソートすれば順序は消える。
仮にソートをやめても、**RDF の複数値に順序は無い**——書き出した JSON-LD を外部のビューアや
SPARQL で読んだ時点で `used[0]` は意味を失う。**属性として持つしかない。**

**名前を `provision:branchedFrom` にする理由**: `prov:PrimarySource` は「一次資料」
（伝聞ではない出所）の意味であって、「主たる親」ではない。`primarySource` と名乗ると
PROV の語と衝突して読み違えられる。`branchedFrom` は「利用者が分岐した版」という実在する
事実を指しており、意味がずれない。**足す語は 1 つだけ**——素の PROV に「主たる派生元」を
表す語が無いので、`provision` 名前空間の最小拡張（D-004）としてここに置く。

### 画像バックエンドが複数入力を取れなくても、記録の形は変えない

mflux の `--image` は 1 枚しか取らない（[`src/image/mflux.ts`](../src/image/mflux.ts)）。
複数参照はモデル側の機能で、取れないなら **Jimp で 2 枚を並べて 1 枚にしてからモデルへ
渡す**という道がある。そのとき記録は次のようになる。**すでにある仕組みにそのまま乗る。**

| 記録 | 値 |
|---|---|
| `used` | 2 枚の親（両方） |
| `provision:branchedFrom` | 利用者が居た方 |
| `provision:conditioningImage*` | **実際にモデルへ渡した 1 枚**（連結画像ならそれ） |

`conditioningImage` は「実際に何を渡したか」を残すために既にある。ここを親のどちらか
1 枚で埋めると、記録から同じ絵を作り直せなくなる（D-002）。

**`image.compose` の性質**: executor は `image-model`、等級は `stochastic`（D-016）、
`pixelOrigin` は `synthesized`（D-020）。**編集専用モードでは使えない。** 2 枚の画像を
継ぎ目なく融合するのは、実験画像では継ぎ貼りそのものである。

**捨てたもの**: 融合の相手を `prov:used` の「参照」（D-006）として扱う形。D-006 の参照は
**機械が消費していない**——人間が見ただけ——ことを表すために点線で描いている。材料として
画素が入ったものを同じ辺で書くと、その区別が消える。

### 会話の外から借りた版も、グラフには置く（実装して分かったこと）

会話は分岐元でたどるので、借りた側はこの会話に属さない。**属さないからといってノードを
置かないと、辺の端点が欠けて ELK が例外を投げ、グラフが 1 本も描かれない**（実測。
prov-jsonld-viz で同じことが起きたのと同型の失敗——D-005 の「端点の無い辺」）。

置いたうえで**破線にし、「別の会話から」と書く**。この会話の版ではないが、
材料として画素が入ったことは事実なので、消してはいけない。

## D-022 指示を節点として置く。**候補は指示から分岐する**

**決定**: 1 回の送信を `prov:Plan` として記録し、その送信から走った Activity を
`prov:hadPlan` で結ぶ。会話の切り出し（`rootOf` / `roots`）はこれを辿る。
**1 本しか走らない送信では作らない。**

**なぜ**（D-018 の判断を覆す）

D-018 で Plan を捨てたときの理由は「束ねて得られるのは操作の回数だけ」だった。
これは**親がある候補しか見ていなかった**。親が無ければ兄弟になりようがなく、
候補 3 枚がそのまま根 3 つ——**会話 3 つ**になる。

| 利用者の見え方 | 記録の形 |
|---|---|
| 1 つ頼んだ | 送信 1 回 |
| 候補が 3 枚出た | Activity 3 本、Entity 3 個 |
| **会話が 3 つに増えた** | 根が 3 つ（親を持たない生成が 3 本） |

束ねて得られるのは操作の回数ではなく、**その候補群がどこから始まったか**だった。
画像を共有していなくても、**指示は共有している**。指示は実在するもので、
「同じ指示に応えて作られた」は道具の操作ではなく**図版がなぜ存在するかの記録**である。

**なぜ `prov:Plan` か**: 素の PROV に「複数の実行が従った計画」を表す語がある以上、
`provision` 名前空間へ新しい語を足す理由が無い（D-004）。`prov:Plan` は
`prov:Entity` の下位なので、読む側に新しい型も増えない。

**`prov:hadPlan` は Association の述語なので、限定表現を通すしかない。** Activity へ
直接書くと定義域が合わず、「W3C PROV に完全準拠する」が嘘になる。JSON-LD には既に
Usage / Generation / Association を実体ノードとして書く形があるので（D-005）、
**その Association に `hadPlan` を足す**。新しいノードは作らない。

**載せる先は人間 Agent の Association だけ。** 計画を持つのは責任者である（D-006）。
ソフトウェアの Agent に計画を持たせると、道具が意図を持ったことになる。

**1 本しか走らない送信では Plan を作らない**

作っても言えることが増えないからである。Activity の `provision:intent` が同じことを
言っており、節点を足すぶんグラフが重くなるだけになる。**Plan があること自体が
「この送信は枝分かれした」という情報**になる。

**会話の導出を変える**

根は「親を持たない生成が生んだ画像」のままだが、**同じ Plan を持つものは最初の 1 件へ
寄せる**。これで 1 つの依頼が 1 つの会話になる。`prov:alternateOf` を辿って元の会話へ
寄せているのと同じ形で（D-011）、**会話は別の語彙で持たない**という前提も保たれる。

**捨てたもの**: 「同じ intent・近い時刻」で会話をまとめる方法。記録から導けるように
見えるが、**偶然の一致を根拠にしている**。同じ指示を 1 分後にもう一度出したら
同じ会話に畳まれてしまう。推測で繋いだ辺は、検査すれば必ず壊れる（D-015 と同じ筋）。

## D-023 保存を求める文は、**作り替えの依頼へ付けない**

**決定**: 画像モデルへ渡すプロンプトに「既存の要素をすべて保て」と書くかどうかを、
編集の範囲（`local` / `whole`）で切り替える。**範囲は指示を読んだプランナーが答える。**
答えなかったときだけ、指示の言葉から当てる。

**なぜ**

「シンプルなフラットデザインにして」の直後に
`Preserve all existing visual elements, composition, colors, and geometry` と書くと
**自己矛盾する**。モデルは保存の方に従い、絵がほとんど変わらない。
利用者の来歴に残っていた実測:

```
Edit the input image according to this instruction: Create a simple flat design logo ...
Preserve all existing visual elements, composition, colors, and geometry unless explicitly changed.
```

「同じ方向性で抽象化をしてほしい」も同じ形で、2 回続けて絵が変わらなかった。

**同じ失敗を 2 度している。** 文字追加の依頼へ `Do not add any text` を付けたときも、
モデルは禁止文へ従って絵が変わらなかった（`prompt.ts` に実測のコメントが残っている）。
**打ち消し合う文を並べると、モデルは制約の強い方に従う。** これは 1 回目の教訓を
「文字追加のとき」に限って読んでいたための再発で、**一般化して書き直したのがこの決定**である。

**なぜ規則ではなくプランナーが決めるのか**

「全体を作り替えるか」は指示の**意味**の問題で、語の一致では決まらない。
プランナーは既に指示を読んでツールを選んでいるので、そこで一緒に答えさせるほうが確かである。
規則は受け皿として残す——**LLM を設定していなくても全経路が使える**という前提（README）を
崩さないため。規則で当てにいくのは、プランナーが答えなかったときだけである。

**新しい語彙は足さない。** 実行された全文は `provision:prompt` に残るので、どちらの文を
出したかは記録から読める（D-018 で候補の書き分けを足したときと同じ筋）。

**捨てたもの**: 保存句を一律にやめる案。「余白を少し広げて」で全体が描き直されたら、
それはそれで指示が通っていないことになる。**どちらに転んでも「指示が通らない」ので、
分けるしかない。**

### 判定は、利用者の言い回しではなく**実際にモデルへ渡る文**に当てる（追記）

最初の実装は利用者の指示だけを見ていた。「かなりリッチな画像なので、**ベタッとした
イラスト**にしてください」は語の一致で拾えず、保存句が付いたまま出た（実測）。
ところが、そのとき実際に走った書き直し文はこうだった。

```
Convert the existing rich logo into a flat, solid illustration style.
```

**モデルが読むのはこちらである。** 言い回しは人によって無限にあるが、書き直し文は
プランナーが英語へ寄せたあとなので、当てにいくならこちらのほうが確かである。
語の一覧に頼る度合いも減る。

**上げることはあっても、下げることはない。** プランナーが `local` と答えていても、
書き直し文が作り替えを求めていれば `whole` にする。ここでやっているのは
「作り替えを頼む文に、保存を求める文を並べない」ことだけで、**余計な保存句を外す方向に
しか動かさない**。逆向き（`whole` を `local` へ落とす）は、絵を変えない方へ倒すので採らない。

### 判定を精密にするのではなく、**外しても壊れない形にする**（この決定の本体）

ここまでの直しは 2 回とも「判定の精度」を上げるものだった。語の一覧を増やし、
書き直し文にも当てた。だが**列挙は必ず漏れる**——実際 2 回とも、載っていない言い方で
落ちている。精度をいくら上げても、**外した瞬間に絵が変わらなくなる**構造が残る。

原因は判定ではなく、**意味の分からない文の後ろに固定の英文を貼っていること**である。

| 形 | 文 | 作り替えの依頼と |
|---|---|---|
| 絶対形 | `Preserve all existing visual elements, composition, colors, and geometry` | **矛盾する** |
| 条件形 | `Do not change anything the instruction does not ask you to change.` | **矛盾しない** |

条件形は、指示が何であれ打ち消し合わない。「フラットにして」ならフラットにすることが
指示なので衝突せず、「余白を広げて」なら余白以外は変えないと読める。
**`unless explicitly changed` を付けるだけでは足りなかった**——前半の強い命令に従われた
（実測 2 回）。従属節ではなく、**文そのものを条件形にする**。

これで `scope` は「作り替えを強く促すか」の補助に降りる。**外しても壊れず、
作り替えが弱く出るだけ**になる。語の一覧に頼る度合いもそこで下がる。

**決めた側（プランナーか規則か）は画面に出す。** 外れたときにどちらを直せばよいか
分からないと、また語の一覧を増やすだけの直しに戻る。来歴へ新しい語は足さない——
実行された全文が残っており、どちらの文を出したかはそこから読めるからである（D-018 と同じ筋）。

## D-024 ポートは決め打ちにしない。**200 が返っただけで自分のサーバだと決めない**

**決定**: サイドカーのポートは既定（8788）から順に試し、`/api/health` が
`{"app":"provision"}` を返したところだけを自分のサーバとみなす。どこにも置けなければ、
**何が起きたかを言って**終わる。

**なぜ**（実測）

利用者の PC では、別の製品（asterism）が同じ 8788 で動いていた。そちらは SPA の
catch-all があるので、`/api/graph` に**画面の HTML を 200 で返す**。

```
GET http://127.0.0.1:8788/api/graph
→ 200 OK / content-type: text/html
```

PROVision は `res.ok` だけを見て「サイドカーが起きた」と判断し、その HTML を JSON として
読もうとして落ちた。画面には `The string did not match the expected pattern.` とだけ出た
——**何が起きているのか分かりようがない**。

| 前提 | 実際 |
|---|---|
| 8788 は自分のもの | **他のアプリが使っていることがある** |
| 200 が返れば自分のサーバ | **他人の画面が 200 で返る** |

どちらも「そうであってほしい」だけの思い込みで、確かめていなかった。

**印を見る。** `/api/health` に `app: 'provision'` を載せ、そこまで一致したときだけ
自分のサーバとみなす。**JSON ですらない応答は他人**として扱う——ここを「空き」に倒すと、
塞がったポートへ起こしにいって時間だけ溶かす。

**ポートを譲る。** 他人が居たら次の候補へ移る。相手を止めさせるのは筋が違う——
**こちらが後から来た**のだから、こちらが避ける。

**駄目なときは理由を言う。** 「サーバに繋がりません」で終わらせない。
どのポートが誰に使われていたかまで出す。これが無かったのが、今回いちばん時間を食った。

**捨てたもの**: 使う前に Rust 側で空きポートを探して JS へ渡す形。確かに堅いが、
Rust と JS の両方を変えることになり、**確かめたい性質（他人を他人と見分ける）は
どのみち JS 側に要る**。まず見分けを入れ、足りなければ次に考える。

### 候補を並べるのをやめ、**OS に選ばせる**（追記）

候補を 5 つ並べる形は**列挙であり、いつか漏れる**——語の一覧で 2 度踏んだのと同じ形で、
「全部塞がったらどうするのか」に答えられない。ポートの取り合いには、**列挙しなくて済む
道がある**。

**0 を渡せば、OS が空いているポートを保証して返す。** 取り合いも競合も原理的に起きない。
割り当てられた番号は、サーバが起動時に出す行から読む。

```
PROVision server: http://127.0.0.1:60464  data=…   ← 実測。OS が選んだ
```

Rust 側は既に子プロセスの出力を `sidecar-log` として流しているので、**こちらは聞いて
いるだけでよい**——Rust もサーバも変えずに済む。

**候補の並びは受け皿として残す。** 名乗りが取れなかったときだけ通る。ここを消すと、
聞き取りが何かの理由で失敗したときに起動できなくなる——**新しい道が塞がったときに
古い道が残っている**ようにしておく。

**印の確認（`app: 'provision'`）は、どちらの道でも通す。** ポートの決め方を変えても、
「そこに居るのが自分か」を確かめる必要は消えない。

### 許可の側も、ポートで縛らない（実装して分かったこと）

ポートを動かせるようにしても動かなかった。**Tauri の HTTP 許可が 8788 に固定**されていて、
それ以外のポートへは**アプリ自身が拒否されていた**からである。

```json
{ "identifier": "http:default", "allow": [{ "url": "http://127.0.0.1:8788/*" }] }
```

拒否は例外として返るので、こちらの判定はそれを「誰も居ない＝空き」と読み、そこへ
サイドカーを起こしては届かず、候補を順に潰していった。**画面には「5 つとも別のアプリが
使っています」と出た——実際には 1 つも使われていないのに。**

**決めた側と許した側の両方を直さないと、ポートは動かせない。** 片方だけ直して
「直った」と言えたつもりでいたのが、この 2 回の失敗の中身である。

**候補ごとに丸々待たない。** 全部外れたときに待ち時間が積み上がり、画面が固まったように
見える（実測: 5 候補 × 30 秒で 2 分半）。1 候補あたりの上限を切る。

## D-025 「あるか」を知りたいだけの場面で、**値を読まない**

**決定**: Keychain の項目を「持っているか」だけ見るときは `security find-generic-password`
を **`-w` 無し**で呼ぶ。値の取り出し（`-w`）は、本当に値が要る場面だけにする。
`security` の呼び出しには**必ずタイムアウトを付ける**。

**なぜ**（実測）

設定画面の AI タブが「設定を読み込んでいます…」のまま返ってこなくなった。
`/api/ai/models` は各モデルについて「鍵が入っているか」を返すが、その判定に
**値を読み出していた**。

`-w` は Keychain の許可を求める。**署名が変わった直後——つまりアプリを更新した直後——は
許可が落ちている**ので、そこで止まる。しかも `execFileSync` は Node のイベントループごと
止めるので、**サーバ全体が固まる**。1 つの表示のために、アプリ全体が応答しなくなっていた。

| 知りたいこと | 呼び方 | 許可を求めるか |
|---|---|---|
| 鍵が入っているか | `find-generic-password`（`-w` 無し） | **求めない**（実測 0.3 秒で返る） |
| 鍵の中身 | `find-generic-password -w` | 求める |

**必要のない権限を使わない**というだけの話だが、外すと止まり方が派手になる。
タイムアウトも併せて入れる——応答が無いのは異常なので、待ち続けるより
「取れなかった」として先へ進めるほうがよい。

## D-026 清書は**任意にしない**。訳し漏れは失敗として扱う

**決定**: `image.generate` / `image.edit` / `image.compose` の清書（`prompt`）を
プランナーの**必須の出力**にする。欠けていたとき、または日本語が残っていたときは、
**ツールの選択はそのままに、清書だけをもう一度頼む**。それにも失敗したら、計画は
残したまま警告を出す。あわせて清書の上限を 600 → 900 字へ広げ、
**曖昧な様式語を視覚属性まで開くことを清書の仕事として明記する**。

**なぜ**（利用者の来歴に残っていた実測）

D-023 で「すべて保て」を外したあとも、指示が絵に届かない版が残っていた。
記録を読むと、原因は保存の文ではなく**清書そのもの**だった。

| 版 | 記録された `provision:prompt` | 何が起きていたか |
|---|---|---|
| 「弓矢を無くして、使う色も１色にしたシンプル板が欲しい」 | `Edit the input image according to this instruction: 弓矢を無くして、使う色も１色にしたシンプル板が欲しい Redraw the whole image ...` | **日本語がそのまま画像モデルへ渡っていた** |
| 「方向性は良いのですが、フラットな感じのイラスト調にしてください」 | `... Restyle the existing logo into a flat illustration style ...` | 訳されてはいるが、**画像モデルが従える語になっていない** |

どちらも `planningMode` は `llm` で、振り分け（`image.edit`）は当たっている。
1 件目は**プランナーが `prompt` を省いただけ**である。指示に
`you may set "prompt"` と書いてあったので、省いても仕様どおりだった。
省かれた先で `plan.prompt ?? instruction` が生の日本語へ落ちる。
flux2 の符号化器は日本語をほとんど汲めないので、**利用者から見ると
「言うことを聞かない」だが、実際には指示が届いていない**。

**なぜ計画ごと捨てないのか**: 捨てると規則ベースへ落ちて別のツールが動く（D-013）。
壊れているのは清書だけなので、**清書だけを埋める**。これは D-014 と同じ形——
壊れた所まで戻って、その一手だけをやり直す。

**なぜ「具体化しろ」と「足すな」を書き分けるのか**

これまでの指示は `Do not invent styles, moods, or elements the user did not request` の
一文で、**利用者が言った様式語を開くこと**まで禁じているように読めた。結果、
「フラットな感じ」は `flat illustration style` で止まる。拡散モデルにとってこれは
ほとんど情報がない。開いた先（`solid fills` / `no gradients` / `uniform line weight`）が
無ければ、絵は元の見た目へ引き戻される。

| 清書がやること | 清書がやらないこと |
|---|---|
| 利用者が言った様式語を視覚属性へ開く | 言っていない主題・物体・文字を足す |
| 削除を「無いこと」としても書く（`no bow, no arrow`） | 言っていない雰囲気や色を決める |

**足した分は隠れない。** 利用者の生の言葉は `provision:intent`、実際に渡った全文は
`provision:prompt` として版ごとに別々に残る（D-003）ので、何を頼んで何が足されたかは
常に突き合わせられる。候補出しで同じ縛りを外したときと同じ理由である（D-018）。

**制約は、範囲を名指しして二度書く**（実測）

同じ seed・同じ親画像・同じモデルで、プロンプトだけを変えて確かめた。

| 清書の書き方 | 結果 |
|---|---|
| 日本語のまま（記録に残っていた版） | 弓矢も手も残り、多色のまま。指示が何も効かない |
| `using a single colour on a plain background` を一度だけ | 弓矢は消え、フラットになった。**色は多色のまま** |
| `one single ink colour; every ring, star and line in that same colour; no second colour, no red, no yellow` | 弓矢が消え、**本当に単色になった** |

3 行目でようやく効いた。**同じモデル・同じ seed なので、差はプロンプトだけ**である。
「1 色にできないのはモデルの限界」ではなく、**制約の書き方が足りなかった**。
削除を「無いこと」としても書くのと同じ原則が、色にも寸法にも当てはまる——
**何にかかる制約かを名指しし、やることと現れてはいけないことの両方を書く。**

**捨てたもの**: 清書を短く保つ（`Max 2 sentences`）。短さ自体には価値がなく、
**具体性と矛盾の無さ**が効く。ただし青天井にはしない——長くすると拡散モデルの
注意が薄まり、変更命令まで効かなくなる。900 字は「変える・保つ・避ける」を
書き切れて、なお 1 つの指示として読める長さである。

### 部分を頼まれたら、**全体の名前を主語にしない**（追記）

「タコの足 1 本が折れ線グラフになったロゴ」を 4 枚出して、4 枚ともタコ丸ごとが出た。
清書はどれも `a single octopus tentacle ... no other limbs` で、D-026 の
「無いことも書く」には従っている。**それでも全体が出る。**

同じ seed・同じモデル・同じ寸法で、言い回しだけを変えて確かめた（3 通りの seed で再現）:

| 清書の書き方 | 結果 |
|---|---|
| `a single octopus tentacle ... no other limbs` | 3/3 でタコ丸ごとが軸の上に乗る |
| 主語から `octopus` を外し、足だけを描写（`a long tapering arm with a row of round suckers`）して `no octopus, no head, no body, no other arms` | 3/3 で足 1 本が折れ線になった |
| `a single tentacle shape` とだけ書く | 折れ線だけになり、タコ要素が消えた |

**名前を書くと、その名前のものが出る。** 打ち消しの一文では勝てない——
`no other limbs` は「腕を描くな」であって、「タコを描くな」ではない。
拡散モデルは主語に引かれるので、**部分を頼むときは全体を名指ししない**のが効く。

規則を 1 行足した（`REWRITE_RULES`）: 部分（足 1 本・葉 1 枚・手）を頼まれたら、
全体の名前を主語にせず、**部分そのものを見分けられる形で描写し**、全体を
「無いこと」として書く。これは D-026 本体の「制約は名指しして二度書く」の続きで、
名指しする相手が**制約ではなく主語**になっただけである。

**負のプロンプトは効かない**（実測）。`--negative-prompt` と `--guidance` を付けた版は、
付けない版と**画素まで同一**だった（z-image-turbo は蒸留モデルで、案内なしで走る）。
「打ち消しは別の欄に書けばよい」という逃げ道は、このモデルには無い。

## D-027 語で判定する規則は、**清書へ当てない**

**決定**: プランナーの清書（`provision:prompt`）に対して、日本語の指示向けに書かれた
語の規則を当てない。とくに**文字消しの定型文は清書を置き換えない**。清書が無いとき
（規則ベース、または清書に失敗したとき）だけ、従来どおり定型文で縛る。

**なぜ**（利用者の来歴に残っていた実測）

```
intent: 方向性はこの形として、弓だけを消して、単色にして、フラット化してください
prompt: Edit the input image. Remove the wordmark and all lettering from the logo.
        Preserve the symbol, line geometry, colors, composition, and background.
        Do not add any text, logo, brand name, or watermark.
```

`planningMode` は `llm`、振り分けも `image.edit` で当たっている。清書も出ていた。
それでも渡ったのは**文字消しの定型文**だった。

`isTextRemovalIntent` は「文字を表す語」と「消す語」の同時出現で判定する。
**当てられていたのは利用者の日本語ではなく、清書の英語**である。清書は
`Remove the bow from the logo ...` のように書くので、`logo` と `remove` が必ず揃う。
定型文は `intent` を**捨てて**置き換わるので、依頼が 3 つとも消えた:

| 利用者の依頼 | 渡った文 | 結果 |
|---|---|---|
| 弓だけを消して | `Remove the wordmark and all lettering` | 弓は残る |
| 単色にして | `Preserve the ... colors ...` | **正面から打ち消される** |
| フラット化して | （どこにも無い） | 何も起きない |

**規則は、書かれた対象にだけ当てる。** これらの語の規則は「利用者が日本語で書いた
指示」を読むために作ったもので、清書は読む対象ではない。清書は D-026 で必須になり、
保持と禁止まで自分で書くようになった——**そこへ別の定型文を上書きする理由が無い**。

**同じ形の失敗を 3 度している。** `Do not add any text` を文字追加へ付けた件（`prompt.ts`）、
`Preserve all existing ...` を作り替えへ付けた件（D-023）、そしてこれ。いずれも
**利用者の依頼と、こちらが足した文が打ち消し合っている**。D-026 で「足す文」を
清書へ寄せたので、残っていたのは**置き換える文**だった。

**捨てたもの**: 清書にも語の規則を当てて二重に守る案。守りではなく上書きになる。

## D-028 グラフでも「いま見ている版」と「さっき生まれた版」が分かるようにする

**決定**: 選択中の版を太い輪で示し、直近の送信で生まれた版に「新」の印を付ける。
選んだ版が画面の外にあるときは、**そこへ寄せる**。倍率は変えない。

**なぜ**

チャットの側は、選んでいる版を枠で、生まれたばかりの版を並びの位置で示していた。
グラフの側には**どちらも無かった**。版が 12 個ある会話では、右の面で候補を選んでも
真ん中のグラフのどこが動いたのか分からない。**同じことを見ているのに、片方でしか
分からない**という状態だった。

**寸法を変えずに示す**

選択を枠の太さで示すと、カードの実寸が変わる。背丈の変化は
`ResizeObserver` が見張っていて（重なりを直すため）、**選ぶたびにグラフ全体が
並び直す**ことになる。影は外側へ広がるだけなので、実寸は 1px も動かない。
「新」の印も同じ理由で、カードの中ではなく**重ねて置く**。

**写し（`toFlow`）には混ぜない**

「新」は記録の性質ではなく画面の状態である。`toFlow` の入力にすると写しが作り直され、
測り直しとレイアウトが丸ごとやり直しになる。選択と同じく、**描く直前に載せる**。

**寄せるのは外に出ているときだけ**

見えているのに動かすと、利用者が自分で動かした位置を勝手に戻すことになる。
倍率も変えない——選び直すたびに拡大率が動くと、どこを見ているのか分からなくなる。

**`duration` を付けない。** アニメーションは `requestAnimationFrame` で動くので、
隠れたタブでは一度も進まないまま終わる（実測。同じ理由で `fitView` にも付けていない）。
位置と寸法は `getNode` ではなく **`getInternalNode`** から取る——`getNode` が返す版は
測る前だと `measured` を持たず、寄せが一度も動かなかった。

**捨てたもの**: 生成のたびにグラフを新しい版へ合わせて拡大する案。派手だが、
**利用者が見ていた場所を奪う**。外に出たときだけ、同じ倍率で寄せるのが控えめで足りる。

## D-029 画像生成環境の導入を、画面のボタン 1 つで済ませる

**決定**: 設定に「画像生成」タブを置き、uv → mflux → 量子化済みモデルの順に
**足りないものだけ**を入れる。uv はアプリに同梱し、mflux / mlx / Python の版は固定する。
生成器が無いときのエラーには印（`code`）を付け、画面はそこから導入へ誘導する。

**なぜ**

初めての Mac で最初に出るのが「画像生成コマンドが見つからない」だった。しかも
README には iopaint と rembg の入れ方はあるのに、mflux 本体の入れ方が無かった。
道具の目的（系譜を残す）に辿り着く前に、環境の整備で止まる。

**版を固定する**

mflux と mlx の版が違えば絵が変わりうる（D-015）。「最新を入れる」導入は、
Mac ごとに違う環境を静かに作り、別 PC で同じ指定が違う絵になったときの容疑者を増やす。
固定した版は Agent の実測（dist-info）にそのまま現れるので、突き合わせの土台が揃う。
mflux 0.18.1 は mlx<0.32 を要求するので、mlx は 0.31.2。

**入っているものは触らない**

既にある mflux を入れ替えたり、4bit があるのに 6bit を足したりしない。
手で整えた環境を壊さないためと、33GB の取得を黙って始めないため。
量子化の選択が効くのは、生成モデルがまだ無いときだけ。

**半端なものを「ある」と見なさない**

置き場の有無で「使える」を決めている（`findSavedModel`）ので、途中で落ちた
ディレクトリがそのまま「ある」になる。モデルは `<名前>.partial` に保存し、
終わってから本来の名前へ動かす。失敗と中止では消す。

**サーバと運命を共にする**

アプリが終わると node は止まるが、その子（uv / mflux-save）は孤児として走り続ける。
次に導入を押すと、同じ置き場へ 2 本が書く。SIGTERM を受けたら子を止めてから exit する。
取りかけの取得は Hugging Face 側が続きから再開できるので、失うのは量子化の分だけ。

**uv は同梱する**

GUI から起動されると PATH が /usr/bin:/bin 程度しか無く、Homebrew の uv は見えない。
アプリの中から `curl | sh` を走らせるのは、何が入るかを配布側で決められない。
node と同じく取得スクリプトで置き、版と sha256 を固定する。同梱が無い開発中は、
手元の uv（`~/.local/bin`、Homebrew）を絶対パスで探し、それも無ければ brew で入れる。

**置き場は Resources ではなく externalBin。** Resources に置いた uv は Tauri が署名せず、
公証が「Developer ID で署名されていない・hardened runtime が無い」と弾いた（v0.2.20 の
ビルドで実測。node が通っていたのは Node.js 側が署名済みの実行ファイルを配っているから）。
externalBin は本体と同じ `Contents/MacOS` に置かれ、本体と同じ署名を受ける。

**進み具合は取り直して読む**

SSE で流す案は捨てた。Tauri の fetch でストリーミングが確実に動くかを確かめる
コストに見合わない。1.5 秒ごとに状態を取り直せば足りる。ログは `\r` を
「直前の行の書き換え」として扱い、進捗バーが数百行に膨らまないようにした。

**エラーは文言ではなく印で見る**

生成のエラーから導入へ誘導するのに、文言の一致で判定すると、文言を直した瞬間に
誘導が消える。`ImageCommandMissingError` に `code` を持たせ、API はそれを返す。

**導入が終わったら Agent を取り直す**

起動時に mflux が無ければ、その Agent は版を持たない。導入直後の最初の生成が
その Agent を指すと、環境の分からない Activity が残る。終わった時点で実測をやり直す。

**捨てたもの**: 起動時に黙って導入を始める案。33GB の取得を利用者の判断なしに
始めるのは、この道具の「何が起きたかを言う」姿勢と合わない。Windows / Intel Mac
への対応は、mflux が MLX でしか動かないので対象外。そこでは `PROVISION_IMAGE_COMMAND` を指す。

## D-030 生成の節点は、意図ではなく**実行された全文（清書）**を見せる

**決定**: グラフの生成（`prov:Activity`）の節点の見出しを、利用者の生の言葉
（`provision:intent`）から、画像モデルへ実際に渡った全文（`provision:prompt`）へ変える。
意図は指示の節点（`prov:Plan`、D-022）が出す。指示の節点が無い 1 本だけの送信では、
生成の節点に意図も添える。清書は**英語のまま**出す。

**なぜ**（利用者の指摘）

候補を 4 枚出すと、指示の節点の下に生成の節点が 4 つ並ぶ。その 4 つが全部、
すぐ上の指示の節点と同じ文を出していた。**候補ごとに違うもの——清書と seed——が
隠れていて、どの清書がどの絵を作ったのか分からなかった。** D-018 の表で
「版ごとに違うもの」と書いたものが、画面では見えていなかった。

実データでも、3 枚の候補の清書は `Flat vector badge with a circular outline...` /
`Flat vector monogram, the letter O shaped as an 8...` / `Flat vector icon on a square
canvas, minimalist 8...` と方向が違っていた。節点はそれを 1 文字も出していなかった。

**なぜ英語のままか**

清書が英語なのは好みではなく、画像モデルの符号化器が日本語をほとんど汲めないため
（D-026 の実測: 日本語のままでは指示が何も効かない）。ここで見せたいのは「この絵を
作ったのは何か」なので、**渡ったものをそのまま出す**。日本語訳を添える案は捨てた——
訳は実行されたものではなく、訳がずれたときに「何で作られたか」を誤らせる。それは
このグラフで一番あってはならない誤りである。読みやすさは、すぐ上の指示の節点が
日本語の意図を出していることで足りる。

**指示の節点が無いときだけ意図を添える**

1 本だけの送信では指示の節点を作らない（D-022）。そのとき生成の節点から意図を消すと、
「なぜこの版になったか」がグラフから消える。両方要るので、意図を上に、清書を下に置く。
確定的なツール（Jimp）や取り込みは清書を持たないので、これまでどおり意図だけを出す。

**捨てたもの**: 節点をホバーしたときだけ清書を出す案。候補を見比べるのに 4 回
ホバーするのでは、並べて出している意味が無い。

## D-031 清書は**利用者が書ける**。手で書いたことは記録に残す

**決定**: どの版からでも、実行された全文（清書）を直して出し直せるようにする。
書いた文は**書き直さずそのまま**画像モデルへ渡し、手（ツール）と入力画像は
その版の記録から引き継ぐ。seed は既定で据え置く。この一手の
`provision:planningMode` は **`author`**（新しい値）にする。

**なぜ**

清書の言い回しで絵が変わることが実測で分かった（D-026 の追記）。ところが清書は
プランナーの出力で、画面からは**読めるだけで直せなかった**。規則を足しても
当たらない指示は残る——そのとき利用者にできることが「日本語を言い換えて祈る」しか
無いのは、この道具が「何が実行されたか」を見せている意味を半分捨てている。
**見せているものを直せるようにする。**

**プランナーを通さない**

手で書いた文を清書に通すと、書き直されて「自分で書いた」が嘘になる。
通さないので、**画面に書いた文がそのまま `provision:prompt` に残る**。
日本語のまま書かれたら止めはしないが、黙りもしない——渡す前に警告を返す（D-026）。

**seed は据え置きが既定**

変えると、絵が変わった理由が清書か seed か分からなくなる。**言い回しの差だけを見る**のが
この機能の目的なので、既定は同じ seed にして、変えたい人だけが変える。

**`planningMode` に `author` を足す。新しい語は作らない**

`planningMode` は「この一手を誰が決めたか」で、`rules`（語で判定する規則）と
`llm`（プランナー）があった。手書きの清書はどちらでもない。`llm` と書けば嘘になり、
空にすれば「記録する前の古い版」と区別がつかない。値を 1 つ足すのが一番小さい変更で、
書き出し・読み込み・差分（`compare.ts`）は既にこの項目を通しているので、
**足すだけで来歴・突き合わせ・画面が揃う**。

**出し直しは兄弟。子ではない**

清書を直した版は、元の版を**材料にしていない**。同じ親から生えた別の試行なので、
`used` は元の版と同じものを指す。同じ送信（`prov:Plan`）にも属させる——
同じ指示に応えた版だからで、これで会話が増えずに候補として並ぶ（D-022）。

**`/api/rerun` とは別の口にする**

あちらは記録どおりに出し直して食い違いを検査するもので、違えば `prov:alternateOf` を
張る（D-011）。清書を変えたものをそこへ通すと、**こちらが変えた差を「食い違い」として
記録する**。検査の意味が消えるので、口を分ける。

**入力画像は記録から引く**

編集範囲を消した画像も、融合で横に並べた 1 枚も、`conditioningImage` に畳まれている
（D-002）。だから引き継ぐのはそれ 1 枚でよく、範囲指定や矢印を画面から作り直す必要が無い。
**再実行に要る情報を全部残しておくと、こういう機能が後から安く作れる**という例である。

**捨てたもの**: 送信欄に「清書を自分で書く」という切り替えを置く案。そこから送ると
いま見ている版の**子**になり、生成のやり直しではなく編集になる。狙いは
「同じ手をやり直す」なので、版に付いた口のほうが形と合う。

## D-032 気に入らない版は**消さずによけておく**

**決定**: 版を 1 つずつ消す機能は作らない。代わりに「よけておく」を置き、候補の並びから
外す。よけたことは**表明**として記録し（D-008）、同じ版への最後の表明が効く。
グラフからは消さず薄く出す。会話をまるごと消す既存の機能はそのまま残す。

**なぜ**

「気に入らない版が散らかる」は本当の困りごとである。だが**選ばなかったことは
図版の来歴の一部**で、D-018 に既にそう書いてあった——「どれを選んだかを明示したく
なったら、生成時ではなく D-008 の表明として後から足す」。よけるのは、その表明そのものである。

**1 版だけ消すと壊れる**（実測）

3 世代の鎖を作り、途中の版だけを消して測った。

| 消し方 | 何が起きたか |
|---|---|
| その版に触れる節点を全部消す | 節点 11 → 6。**残したかった孫の版まで消えた** |
| 子を残して途中の版だけ消す | 子が自分自身を根とする**別の会話**になり、会話が 2 つに割れた |

後者では、子の記録が「もう存在しない版から派生した」と主張したまま残る。書き出した
JSON-LD を外から読むと、辿れない派生の辺になる。描画自体は落ちなかった
（端点の無い辺は 0。`toFlow` は見つからない版を飛ばす）が、**系譜としては嘘になる。**

**容量は理由にならない**（実測）

```
画像 12MB（34 枚） / キャッシュ 16MB / グラフ 200KB
モデル 7.9GB / Hugging Face キャッシュ 57GB
```

画像を全部消してもモデルの 0.02% 程度しか空かない。しかも同じ絵はキャッシュにも
残るので、片方だけ消しても実際には減らない。

**形は表示名の変更と同じ**

表明を 1 本足し、同じ版への最後の表明が効く。**戻すのも「戻した」という表明**なので、
よけた事実は消えない——いつ誰が言ったかが残らなければ表明にならない（D-008）。
新しい語は `provision:archived` の 1 つだけで、置き場は表明 Activity に限る。

**いま見ている版は隠さない**

選んでいるものが並びから消えると、自分がどこに居るのか分からなくなる。よけた印を
付けたまま残し、その場で戻せるようにする。

**グラフからは消さない**（当初の判断。下で改める）

系譜の途中の版は**派生元でもある**。グラフから抜くと、子の版が「どこから来たか」を
辿れなくなる——上の実測で測った 2 つ目の壊れ方を、見た目だけで作ることになる。
薄くして印を付けるにとどめる。

**捨てたもの**: 子を持たない版に限って本当に消す案。技術的には安全だが、容量が
理由にならない以上、消して得られるのは「試した事実を失うこと」だけである。
会話まるごとの削除は残す——あちらは系譜が自己完結しており、既にコードにも
「残す意味があるなら消してはいけない」と立場が書いてある。

### グラフからも外す。ただし**子は繋ぎ直す**（追記）

薄く出す案は、使ってみて否だった。**散らかるのを止めたくてアーカイブしたのに、
グラフには居座る。** 薄いぶん読みにくくなるだけで、目的を果たしていない。外す。

外すと辿れなくなる、という当初の心配は**繋ぎ直せば消える**。隠した版に子がいるときは、
**その上の見えている一番近い版へ辺を張る**。直接の派生ではないので細い点線にして、
間に何かがあることは見た目で分かるようにする。根まで全部隠れているときは繋ぎ先が無いので、
子はそのまま根として描く。

これで、当初の心配（子がどこから来たか辿れない）と、利用者の要求（散らかるのを止める）が
両立する。**辺を落とすのが問題だったのであって、節点を外すこと自体ではなかった。**

切り替えはグラフの面の右上に置く。**在ることは言う**——黙って消すと、作ったはずの版が
失われたように見える。切り替えはチャットと共有する 1 つの状態にした。別々に持つと、
片方で出しているのにもう片方では消えている状態が作れてしまう。

**言葉は「アーカイブ」にする。** 「よけておく」は他の文言（材料を足す・矢印を引く）と
そろえた案だったが、何が起きるのかが伝わらなかった。戻せることまで含めて、
アーカイブのほうが通じる。
